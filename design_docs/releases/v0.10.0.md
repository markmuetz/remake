# v0.10.0 — provenance capture + preparing the 1.0 freeze

> **Draft 2026-11-21** (Claude, from the [roadmap](../roadmap.md) 0.10.x
> milestone, [discussion.md](../discussion.md) "Provenance & history" and
> "Outputs, storage & on-disk layout", and what 0.9.0 left open). All
> decisions answered by MM 2026-11-22. See
> [Decisions](#decisions).

0.10 is the last minor before 1.0. After 1.0 the remakefile DSL, the public
Python/CLI API and the on-disk format are bound by
[compatibility.md](../compatibility.md): SemVer, deprecation ramps, automatic
migrations. So 0.10 has two jobs:

1. **Start recording what can't be recovered later.** Environment and git
   state per run, and per-execution history. Exports after 1.0 (RO-Crate,
   `remake report`) can only be as rich as the history that exists by then.
2. **Settle every surface 1.0 will freeze**, so that 1.0 itself is a
   declaration, not a round of breaking changes.

Breaking changes are still allowed in 0.10 (minor lane, changelog
**Breaking** notes). Anything to be removed at 1.0 must warn in 0.10.

## Items

### 1. Provenance capture

**What:** each `run` row (0.9.0 added the table: `run_seq`, `started`,
`remakefile`, `command`, `config`) also records:

- **git:** the commit of the repo holding the remakefile, whether the work
  tree was dirty, and (if dirty) a hash of `git diff HEAD`, so two dirty
  runs can be told apart. Nothing if not in a repo, or no `git`.
- **environment:** the Python version, remake's version, and an
  environment fingerprint: a sorted `name==version` list of installed
  distributions (`importlib.metadata`, no subprocess), hashed. The full
  list is stored once per distinct hash (interned, like run code), so
  `remake` can show what changed between two runs. A lockfile next to the
  remakefile (`uv.lock`, `pixi.lock`, `conda-lock.yml`) is hashed too, if
  present.
- **host and user** (already wanted by item 3; privacy below).

**SLURM:** jobs can run in a different environment from the planner. That
is what `check-env` exists for. Each array job computes the same fingerprint
and writes it to its sidecar only if it differs from the planning run's;
ingest records it against the tasks it ran. `task-info` then says "ran in a
different environment from the one that planned it".

**Never a rerun trigger.** Provenance is recorded, not compared, exactly
like checksums and config in 0.9.0. A changed environment shows in
`task-info` and `why`, but doesn't rerun anything. (Whether it *could*, as
opt-in, is a question for after 1.0.)

**Cost:** one `git` call and one metadata scan per invocation (tens of ms;
measure). Must not slow `run-task`/`run-array-task` startup measurably:
compute lazily, only when the fingerprint is needed.

**Schema:** additive (minor bump): columns on `run`, plus an interned
`environment` table. Older DBs read as "not recorded".

### 2. `remake verify`

The persistent, explicit sibling of the transient `check_outputs` modes.
**Read-only by default; `--apply` writes.** `-Q`-composable.

- **`--outputs`** (discussion (a)): DB says success, output missing or
  failing its `Ensure` checks on disk → report; with `--apply`, mark the
  task pending. Scratch-purge recovery.
- **`--adopt`** (discussion (c)): no record, outputs complete on disk →
  report; with `--apply`, mark success with the current code. Adopting an
  existing output tree.
- **Not built in 0.10:** mtime staleness (discussion (b)). remake is
  DB-first because mtimes are unreliable on HPC. If it is ever built it
  stays behind `--mtime`, only for inputs no rule produces.

Uses batched listing from item 5a (one directory scan, not one `stat` per
file), so it is usable at 1e6 files. `--json` output.

**Overlap to resolve:** `set-state --success --check-outputs` already
adopts. Proposal: keep `set-state` as the "I know what I'm doing" stamp,
make `verify --adopt --apply` the recommended path, and have
`set-state --check-outputs` print a pointer to `verify`. No removal.

### 3. Minimal run history

**What:** one row per task *execution* (today a task keeps only its last
execution): task, `run_seq`, status, wall/CPU/peak RSS, output bytes, the
rerun reason category (`explain_task` already computes it), host, error
signature. Plus per-run counts on the `run` row (planned, run, succeeded,
failed, skipped, waves).

**Read side, minimal:** `remake history <task>` (that task's executions)
and `remake history --runs` (recent runs, one line each), both with
`--json`. No dashboard, no aggregates beyond what one SQL query gives; the
HTML report after 1.0 reads this.

**Where it lives:** see decision D3. discussion.md argued for a separate,
disposable `.remake/stats.db`. 0.9.0 has since put `run` and `output_stat`
in `remake.db`.

**Retention from day one:** a row cap per task (default: keep the last 20
executions) and `remake history --prune`.

### 4. Scale work driven by field data

- **CI gate: done.** The `bench` job in `ci.yml` (py3.13, separate from the
  test matrix) runs `tests/benchmarks/bench_field_scale.py --json` at the full
  size (1e4 tasks × 100 files; it takes ~2 s, so no reduced size was needed)
  and then `tests/benchmarks/check_regression.py`. A phase fails if it exceeds
  2.0 × the baseline plus 0.15 s slack (so millisecond phases do not trip on
  noise). The baseline is scaled by a pure-Python calibration loop to allow
  for runner speed. A phase missing from the baseline is a warning.
  Baseline: `tests/benchmarks/baseline_field_scale.json`, the median of 5
  local runs on an Apple M5 (macOS, 2026-11-22), not yet from a CI runner.
  Refresh: run the benchmark 5 times with `--json`, take per-phase medians
  and update the metadata. After the first CI runs, check the runner's
  numbers and rebase the baseline on them if the scale factor is far from 1.
- **The file-side frontier: done** for planning under `check_outputs`
  ('fallback'/'always'), `verify` and the missing-inputs check, which go
  through `tokens.complete_many` (one `os.scandir` per directory holding 8+
  markers, a `stat` each below that; Dir and Ensure-checked outputs still
  read per token). `ls-tasks --check` still checks per file (it streams).
- Driven by numbers from a real JASMIN pipeline: before starting, time
  `remake info` and `run -n` on the largest field remakefile and record the
  results here.

### 5. Settle the frozen surfaces

**5a. Output-token interface.** Freeze `OutputToken` as a documented public
base class: `identity`, `is_complete`, `format`, plus 0.9.0's
`before_run`/`validate`/`after_success`. Add, so storage backends (S3 etc.)
can come after 1.0 without changing the interface:

- `stat()` → size (and existence) without reading the data;
- a batch form, `Token.complete_many(tokens)`, defaulting to a loop, which
  local paths implement with one `os.scandir` per directory;
- identity normalisation: one canonical spelling per output (absolute,
  normalised), used by lint, the missing-inputs check and Dir ownership.
  0.9.0 normalises separately in each; make it one.
- `remote` (bool): remote tokens are skipped by plan-time checks (0.9.0
  does this with an `isinstance(PathToken)` test).

**5b. `--json` shapes.** Every `--json` output gets a top-level
`"format": 1` and an object (not a bare list) at the top. Documented in
`docs/cli.md`. After 1.0, adding fields is fine; removing or renaming one is
a major change.

**5c. Exit codes.** Documented today as 0 / 1 / 2 / 130 / 143. Decided:
"a rule was left blocked" (deferred matrix never ready) gets its own code,
3, distinct from "a task failed", 1 (D5).

**5d. `Remake` method naming.** Audit the public methods against the CLI
verbs (`task_info`, `rule_info`, `set_state`, `missing_external_inputs`,
`plan`, `run`, …). Rename for consistency now, with the old names kept as
deprecated aliases until 1.0. **Library use:** a `Remake` built in a
notebook resolves relative paths against the cwd, not the remakefile's
directory as the CLI does. Decided: it always anchors to the defining file's
directory (D6).

**5e. The declared public API.** `docs/api/` lists what is public; give
`remake/__init__.py` an `__all__` that matches it exactly. Everything else
(`remake.core.*`, `remake.util.*`) is internal and may change after 1.0.
A test checks the two agree.

**5f. Where `.remake/` lives.** Options (discussion.md):
(i) next to the remakefile, as now;
(ii) configurable, via a `metadata_dir` key in `remake.toml`;
(iii) automatically next to the output tree.
Decided: (i) as the default plus (ii); reject (iii), which breaks when one
pipeline writes to several trees or several pipelines share one (D7).

### 6. Design check: `temp()` and scratch after 1.0

Not built in 0.10. The deliverable is a short design note
(`designs/temp_outputs.md`) that confirms the feature can be added after 1.0
**without a breaking schema or DSL change**. The case to check: an output
that is "complete in the DB, may be absent on disk, rebuild only if a
consumer reruns" (discussion.md). Candidate: a nullable `deleted` column on
`output_stat` (an additive minor), and a token flag (`temp(...)`, like
`Ensure`). If the check finds it would need a breaking change, that change
happens in 0.10.

### 7. DSL debts carried from 0.9.0

All change what a remakefile may contain, so they are 1.0 blockers:

- **Bug 02** (`task-info` crashes when an input value isn't a single path)
  and **review L2** (`{'files': ['a/{i}', 'b/{i}']}` is stringified into one
  bogus path). Decided: list-valued entries are supported throughout
  (formatted per element; lint, checks and `task-info` see each path) (D8).
- **Module scans claim the wrong rules:** `rules_from_current_module()`
  misses rules held in lists or dicts (documented in 0.9.0), and would claim
  a rule *imported* from another remakefile into this pipeline. Fix: scans
  take only objects *defined* in the scanned file; warn on unregistered
  Rules held in containers (todos.md).
- **One environment report:** merge
  `executors/slurm_executor.environment_report` and
  `envcheck.environment_report`. Item 1 is when they change, so do it there.
- **Remove at 1.0, warn in 0.10:** the built-in JASMIN SLURM defaults
  without `--profile` already warn (0.9.0). List here anything else 0.10
  deprecates.

## Decisions

Answered by MM on 2026-11-22: Claude's recommendation for all but D6
and D9.

- **D1. Environment fingerprint: decided.** Installed distributions via
  `importlib.metadata` (portable, no subprocess), plus a lockfile hash if
  one is present.
- **D2. git capture: decided.** Commit + dirty flag + diff hash. The diff
  itself is not stored (size, secrets).
- **D3. Where history lives: decided.** In `remake.db`, with a row cap per
  task: one file, joins work, SLURM sidecars already write there.
- **D4. Host and user in the record: decided.** Hostname in plain text,
  username only as a hash. An archived `.remake/` or a later RO-Crate could
  expose them.
- **D5. Exit code for a blocked rule: decided, 3.** When `remake run`
  ends because a rule could never run (a deferred matrix whose inputs never
  appeared, so its tasks were left blocked) and no task failed, it exits 3,
  not 1. Scripts can then tell "something is broken" (1) from "the run
  stopped short and needs another pass" (3). A task failure still gives 1,
  even if rules were also left blocked.
- **D6. Library anchoring: decided, always anchor.** A `Remake` resolves
  relative paths against the directory of the file that defines it, in
  library use as in the CLI, never against the cwd. Detail for
  implementation: where there is no defining file (a notebook cell, the
  REPL), fall back to the cwd and say so in the docs.
- **D7. `.remake/` location: decided.** Next to the remakefile by default,
  plus a `metadata_dir` key in `remake.toml`. Co-locating with outputs is
  rejected.
- **D8. List-valued inputs/outputs: decided.** Supported throughout:
  formatted per element, and lint, checks and `task-info` see each path.
- **D9. Python 3.10: decided, dropped in 0.10.** It reached end of life in
  October 2026, tornado 6.6 (the 4 open Dependabot alerts) needs 3.11+,
  and `tomllib` is built in from 3.11. `requires-python = ">=3.11"`, CI
  matrix 3.11–3.14, the `tomli` fallback removed, **Breaking** note in the
  changelog.
