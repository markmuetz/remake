> **Draft 2026-11-22** (Claude, from what 0.10.0 left open: the

The roadmap goes from 0.10 straight to 1.0. That assumed 0.10 would leave
every frozen surface settled. It left a few things that would be breaking to
change after 1.0, and two of the release's safety checks are still manual. So
0.11 is a short **hardening** minor: no new features, only the work that
gates 1.0 by the roadmap's own test ("does 1.0 need it?"), plus a field soak
that gives "judged stable" some evidence. 1.0 then contains almost nothing
new (see [What goes in 1.0](#what-goes-in-10)).

Every item either settles a surface 1.0 freezes (the remakefile DSL, the
public Python/CLI API including `--json`, the on-disk format) or protects the
correctness of what is stored. Additive work (an environment-diff command,
`remake report`, RO-Crate, `temp()`) stays after 1.0.

## Items

### 1. Upgrade safety as CI

Two release gates are manual today: "upgrading reruns nothing", checked at
0.9.0 and 0.10.0 by running the examples under the previous PyPI release and
planning them with the branch; and "opens every older DB". Both caught real
problems in 0.10 (the list digest, the 3.14 SQLite rebuild), so they should
run on every push.

- **`upgrade` CI job:** install the previous release from PyPI into one venv
  and the branch into another. Run every stdlib example with the old one,
  then `run -n` with the new one, and fail on any task that would rerun.
  Include list values, callable specs returning Paths, `uses=`, Ensure, Dir
  and a symlinked Dir: the cases 0.10's reviews found by hand.
- **DB fixtures:** a small `remake.db` (and `.remake/` sidecars) produced by
  each of 0.8.5, 0.9.0 and 0.10.0, committed under `tests/fixtures/`. A test
  opens each, migrates, plans 0 reruns, and checks the previous release can
  still read the migrated DB, where the policy promises it.
- **Golden hashes:** task keys, `io`/`uses` hashes and `paths_digest` for a
  fixed corpus of rules, stored as JSON. Any change fails a test that names
  the rule and the field, so a rerun-causing change is a deliberate act.

### 2. A restricted query language for `-Q`

`make_predicate` compiles the query with `eval` (hardened in 0.8.4, but not a
sandbox; MM's comment in `core/planner.py`). After 1.0, narrowing what `-Q`
accepts is a break, so settle the grammar now.

**Approach (Q2, MM: follow pyquerylist,** `~/projects/local/pyquerylist`,
`Query._expr_validate_find_inputs`): parse with `ast.parse(mode='eval')`,
walk every node and reject any whose type is not in an allowlist, naming the
node type and the query in the error; only then evaluate the validated tree
with `__builtins__` set to None and the task's kwargs plus `rule` as the
only names. Allowlist: `Expression`, `Name`/`Load`, `Constant`, `List`,
`Tuple`, `Compare` with `Eq NotEq Lt LtE Gt GtE In NotIn Is IsNot`,
`BoolOp` with `And Or`, `UnaryOp` with `Not` and `USub` (negative numbers).
Differences from pyquerylist, deliberate:

- no arithmetic (`BinOp`), sets or dicts (MM: the defaults);
- `not` allowed (pyquerylist has no `UnaryOp`);
- no "must contain a comparison" rule, because `-Q True` (every task) is
  the documented way to select all for `set-state`;
- no calls, so `QUERY_BUILTINS` (`len`, `range`, `str`, ...) goes: a
  **Breaking** note in the changelog. No `-Q` in the docs, examples or field
  notes uses one (checked 2026-11-22).

Unknown names stay an error (the existing typo check).

### 3. Dependency matching on canonical paths

Lint, the missing-inputs check and Dir ownership compare canonical paths
(0.10 item 5a). Dependency matching between tasks (`deps._norm`,
`planner._norm_paths`) still compares `normpath` strings. When an input
spells a file differently from its producer (absolute vs relative, `./`, a
symlinked root), the task depends on every upstream task. That is safe (it
over-reruns, never misses a rerun) but surprising, and 1.0 users will build
expectations on it. Switch both to `tokens.canonical`, keeping the
template-level fast paths in `deps._classify`. Benchmark: 1e6 paths must stay
within the CI gate (`plan_fallback_stats`, `resolve_outputs`).

Only the *task* level uses paths: rules are linked by `depends_on` alone,
never inferred from paths. Within a declared `depends_on` edge, which
upstream tasks a task reads is matched from paths (`core/deps.py`, review
2026-09-24 H3; docs/guide/rules-and-tasks.md "Which upstream tasks a task
depends on"). In plain terms (Q3): when task B reads a file task A writes,
remake links them, so rerunning A reruns B. It finds the link by comparing path strings.
If B names the file differently (`/home/me/proj/data/a.nc` where A wrote
`data/a.nc`), the strings don't match, and remake plays safe: B is treated
as reading *every* task of A's rule, so rerunning any one A task reruns all
the B tasks. After this change both spellings match, and only the B tasks
that really read the rerun file rerun. The question is whether that change
of behaviour (fewer reruns than 0.10 for such pipelines, never fewer than
needed) is acceptable in a minor release: **yes** (Q3). Changelog: Changed.

### 4. On-disk layout: settle job specs and per-task logs

- **Job specs** (`.remake/jobs/<rule>.<n>.json`) repeat the planner's
  environment fingerprint and the rerun reason in every task's entry. Move
  the per-submission fields (`env`, `run_seq`, format `v`) to a header
  object, keep per-task fields per task, and keep reading the 0.10 shape.
  This is the last chance to change it without a migration promise.
- **Per-task logs** (`.remake/tasks/log/`): one file per task, no total
  cap (todos.md; the open question in per_task_logging.md). Q4 (decided):
  one file per task, overwritten on each run, deleted with its task. As
  built: nothing ever deletes a task record (`delete_tasks` has no
  caller), so "with its task" means when the task leaves the pipeline: `remake
  history --prune` deletes the logs of tasks no longer in it.
- Write down, in compatibility.md, exactly which files under `.remake/` are
  the on-disk contract and which are caches or scratch (`tasks/running`,
  `submit.sh`, logs).

### 5. Property tests for keys and digests

The design doc has promised Hypothesis tests since 0.8 and none exist. Cover:
task key uniqueness and stability over matrix forms (dict, list of dicts,
tuple keys) and value types; matrix normalisation; `paths_digest` and the
io/uses renderings being order-insensitive where documented. Together with
item 1's golden hashes, this is what makes freezing the hashes safe.

### 7. Deprecations and the 1.0 removal list

After 1.0, anything kept can only be removed at 2.0. These are deprecated
now, kept through 0.11, and removed in 1.0 (Q6, decided):

| Deprecated | Since | Replacement | Warns? |
|---|---|---|---|
| `Remake.status_summary()` | 0.10 | `Remake.info()` | yes |
| `Remake.task_spec()` | 0.10 | `Remake.export_task()` | yes |
| `Dir.claim()` | 0.10 | `Dir.adopt()` | yes, since 0.11 |
| Built-in JASMIN SLURM defaults when no profile is selected | 0.9 | `--profile jasmin` (or `[slurm]` in config) | yes |

Removing the JASMIN defaults means a run with `-E slurm` and no profile or
`[slurm]` settings submits with SLURM's own defaults instead of
`partition=standard`, `qos=standard`, 4 h, 4 GB.

### 8. Output readability across all commands

Added 2026-11-23 at MM's request, from the soak (field notes 4 and 5 in
[soak_0_11.md](../records/soak_0_11.md)). Work on a branch
`output-readability` off `release/0.11.0`, merged before tagging.

Audit every command with human-facing output: info, lint, why, history,
rule-dag, dag, ls-tasks, rule-info, task-info, task-log, slurm-status,
check-env, verify, config, the run / `--dry-run` log lines and error messages.

- **a. One table helper** for all multi-row output: header row, aligned
  columns, right-aligned numbers, optional TOTAL row, width-aware (shorten
  long paths with `…/`; truncate at the terminal width, don't wrap).
- **b. One path-display helper:** shorten common prefixes, show paths
  relative to the remakefile's directory where possible, and diff two paths
  as `lint` does (`remake/util/pathdiff.py`).
- **c. One vocabulary:** up-to-date / stale / failed / pending / deferred, and
  SLURM states (PD / R / CD / F) spelled the same everywhere, with a legend
  in `--help`.
- **d. Colour only through `Painter`,** with `--colour` honoured everywhere and
  also accepted after the subcommand (`remake info --colour never` is
  "unrecognized arguments" today; only `remake --colour never info` works).
- **e. No raw reprs, dicts or tracebacks in normal output.** Long one-line
  messages (lint's MISSING DEPENDENCY, ~260 characters) get the stacked
  layout.
- **f. Every command with text output also has `--json`,** and the text is
  rendered from the same data.
- **g. Counts say what they count.** lint's `external: 204 input(s)` counts
  per-task occurrences of 17 distinct files; say "204 inputs (17 distinct
  files)".

Checks, so it stays fixed:

- Golden (snapshot) tests of each command's text output on a small fixture
  project, at 80 and 120 columns with `--colour never`; MM reviews them once,
  then they are pinned.
- A test that no line exceeds the width (bar unbreakable paths) and that
  table columns align (each column starts at the same offset on every row).
- A test that each command's `--colour always` output with the ANSI codes
  stripped equals its `--colour never` output.

`--json` shapes don't change in this item (they are already the 1.0
surface), except to add `--json` where a command lacks it.

### 9. SLURM: tasks killed without a result

Added 2026-11-23 from soak finding 7; design and log in
[designs/slurm_reconcile/](../designs/slurm_reconcile/README.md).
Submitted tasks are PENDING until their results arrive, so a task SLURM
killed is rerun, never taken as up to date. Per-submission job-id records;
`slurm-status` counts lost tasks; `why` and `task-info` show what SLURM
says (squeue, then sacct on demand). Nothing about a kill is stored. A
larger first plan (a sacct-based reconcile and an end-of-submission job)
was dropped as too complex. The continuation being cancelled by any
failure stays documented, not fixed.

## What goes in 1.0

With 0.11 done, 1.0 is deliberately small: it changes no behaviour except
the removals, and turns the promises on.

- The four removals in item 7 (Q6).
- Fixes from the 0.11 soak that are too big for a 0.11.x patch, if any.
- The contract switched on: compatibility.md's "1.0 contract" stated as
  binding from 1.0.0, `docs/api/` checked against `remake.__all__`, the
  PyPI classifier from "3 - Alpha" to "5 - Production/Stable", and a
  stability statement in the README.
- The usual gates: the upgrade CI job (item 1) green against 0.11, the
  JASMIN check, the pre-tag review, releasing.md.

Nothing additive: `remake report`, RO-Crate, `temp()` and the rest start in
1.1.
