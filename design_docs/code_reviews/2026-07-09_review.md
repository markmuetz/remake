# Code review: SLURM submission logic — 2026-07-09

**Scope**: `src/remake/executors/slurm_executor.py` and its integration points
(`remake run-array-task` / `remake resubmit` in `src/remake/remake_cmd.py`,
sidecar readers, planner handoff). Docs excluded per review instructions.

**Method**: `/code-review high` — 7 finder angles (line-by-line, invariant/crash-window,
cross-file tracer, reuse, simplification, efficiency, altitude), candidates deduped,
then an independent verifier pass per candidate (CONFIRMED / PLAUSIBLE / REFUTED).
Nothing was refuted. 12 correctness findings + 5 cleanup findings survived.

A recurring theme: the module's own invariant (docstring lines 17–20 — "rewriting a
rule's JSON spec would corrupt the array indices the queued jobs read") is protected
by exactly one guard, already-queued detection, and findings 1–3 are three independent
ways that guard fails open. Fixing the invariant at the root (immutable per-submission
spec files, e.g. `<rule>.<run_seq>.json`) would collapse findings 1, 2, 3 and 4.

---

## Correctness findings (ranked most-severe first)

### 1. Already-queued detection fails open on squeue error — CONFIRMED
`slurm_executor.py:88-90`

`squeue_snapshot()` catches `FileNotFoundError`/`CalledProcessError` (e.g. a transient
slurmctld timeout on a busy cluster), logs at **debug** level only, and returns `{}`.
`_active_jobids()` is then empty, `_queued_jobids()` returns `[]` for every rule, and
`run_tasks` rewrites `.remake/jobs/<rule>.json` for rules whose previous arrays are
still queued, then submits duplicates. There is no other guard: the planner still
lists queued-but-unfinished tasks (queue state is deliberately not in the DB), and
`run-array-task` (`remake_cmd.py:421-422`) blindly indexes `specs[index]`. Queued
elements read the rewritten spec → wrong task or IndexError, plus concurrent duplicate
execution racing on outputs.

**Failure scenario**: rule with pending array; `remake run --executor slurm` during a
one-off squeue timeout → spec rewritten, duplicates submitted, queued elements run the
wrong tasks.

**Fix direction**: distinguish "queue state unknown" from "queue empty" — raise (or
refuse to submit) on squeue failure, and log at warning+.

### 2. Mid-rule sbatch failure leaves individual jobs live but unrecorded — CONFIRMED
`slurm_executor.py:281` (generated submit.sh), `set -e` at line 164

For individual (below-threshold) rules, submit.sh runs N `JOB_<rule>_<i>=$(sbatch ...)`
lines and echoes the jobids sidecar only **after all N**. A failed `VAR=$(cmd)`
assignment does abort under `set -e`, so one mid-rule sbatch rejection (QOS /
MaxSubmitJobs limit — routine on JASMIN) leaves jobs `0..k` queued with no sidecar
record. The next run finds nothing queued for the rule, rewrites the spec those live
jobs read, and resubmits all tasks → duplicate concurrent execution + index corruption.
(The array branch is safe: its single sbatch line precedes the sidecar echo.)

**Fix direction**: write the sidecar incrementally (append after each sbatch), or
submit from Python per rule and write the sidecar immediately per successful sbatch
(see also finding 6 and cleanup C4).

### 3. Active-state filter misses suspended/held jobs — CONFIRMED
`slurm_executor.py:315`

`_active_jobids` counts only `PD`/`R`/`CF`. Real squeue `%t` codes for jobs that
persist and will still run (and re-read their spec) include `S` (suspended via
`scontrol suspend` or gang-scheduling preemption), `ST`, and the hold/requeue family
`RH`/`RD`/`SE`. A rule whose array is suspended is treated as not queued → spec
rewritten, duplicate array submitted; the suspended job resumes into the new spec.

**Fix direction**: invert the filter — treat as active every state that is not
terminal (`CD`/`F`/`CA`/`TO`/`NF`/`OOM`...), or use `squeue --states=all` minus
terminals.

### 4. Whole-rule skip strands new tasks while downstream still submits — CONFIRMED
`slurm_executor.py:167-172`

When a rule is skipped as already-queued, tasks the *current* plan added (e.g. matrix
grown from n=1..10 to n=1..20) are silently not submitted — but downstream rules with
a **static** matrix are fully planned (the planner defers only deferrable-matrix
descendants; there is no task-level DAG) and get `--dependency=afterok:<old jobids>`.
Downstream tasks n=11..20 start when the old n=1..10 job finishes, with inputs never
produced → spurious failures recorded.

**Fix direction**: per-submission immutable spec files would let the executor submit
exactly the not-yet-queued tasks instead of skipping the whole rule; short of that,
downstream tasks whose upstream tasks were skipped must be skipped too.

### 5. Tuple kwargs are recorded under a phantom task key — CONFIRMED
`remake_cmd.py:427` (`run-array-task`), `task.py:42-43`, `sidecar.py:50`

The documented contract (module docstring line 16) is "kwargs must be
JSON-serialisable". Tuples satisfy it — but round-trip as lists. `run-array-task`
rebuilds the task from `spec['kwargs']` and **ignores `spec['task_key']`**;
`Task.key` is `sha1(repr(sorted kwargs))` and `repr((1,2)) != repr([1,2])`, so the
result sidecar is written under a key the planner never looks up. The task stays
pending forever and is resubmitted on every run.

**Fix direction**: pass `spec['task_key']` through and use it for recording (or
assert recomputed key == submitted key and fail loudly); tighten the contract check
at spec-write time.

### 6. `remake resubmit` re-executes submit.sh with no queue check — CONFIRMED
`remake_cmd.py:440`, literal ids baked at `slurm_executor.py:171`

Resubmit runs `bash .remake/submit.sh` with no already-queued check, no replanning,
no warning: still-queued rules are submitted again (two writers per output), and the
sidecar echoes overwrite the previous jobids, orphaning the originals so the next
`remake run` can rewrite specs they still read. Additionally, submit.sh freezes
**literal** jobids into downstream `--dependency=afterok:` flags for rules that were
already queued at generation time; after those jobs are purged (MinJobAge), sbatch
rejects the dependency and `set -e` aborts the script halfway.

**Fix direction**: resubmit should run the same already-queued detection (or replan);
job-id resolution belongs at execution time, not baked into the artifact.

### 7. `aftercorr` chosen by kwargs equality, not data dependence — CONFIRMED
`slurm_executor.py:251-257`

Element-wise dependency (`aftercorr`) is selected when upstream/downstream kwargs
lists are equal. Equal kwargs do not imply element-wise dependence: `inputs` may be
an arbitrary callable of kwargs (`rule.py:18`), so a stencil rule (task t reads
upstream t-1, t, t+1) has identical matrices yet gets `aftercorr` — downstream
element t starts when upstream t alone finishes and reads a not-yet-written t+1
output. Silent wrong/partial data, no SLURM error.

**Fix direction**: derive correspondence from `task.inputs`/`task.outputs` (plain
paths, available at generation time) and fall back to `afterok` unless provably 1:1.
Note: `remake3_design.md:492-499` asserts the elementwise assumption — the design doc
shares this hole.

### 8. Continuation job can self-replicate without termination — CONFIRMED
`slurm_executor.py:190-198`, caller `remake.py:693`

`run_tasks([], deferred)` is reachable (`remake.py:693` only short-circuits when both
runnable and deferred are empty). Then `submitted` is empty, `all_refs == []`, and
submit.sh contains a single **dependency-less** continuation job that immediately
reruns `remake run --executor slurm`. If the plan is stable (constructible: upstream
recorded success, its output deleted under default `check_outputs='never'` → matrix
keeps raising Defer with nothing runnable), each continuation submits another,
forever. No guard: the continuation writes no sidecar for `_queued_jobids` to catch.

**Fix direction**: refuse to submit a continuation when nothing was submitted this
run (nothing to wait for ⇒ replanning now cannot yield more than replanning already
did), or pass a generation counter and stop after N.

### 9. Continuation lacks `--kill-on-invalid-dep`, pends forever on upstream failure — CONFIRMED
`slurm_executor.py:67-73` vs 45/58, dependency at 195

The per-rule templates set `--kill-on-invalid-dep=yes`; the continuation template
does not, while being submitted with `afterok` over every submitted ref. One failed
upstream task makes `afterok` unsatisfiable; with SLURM's default
`kill_invalid_depend=no` the `remake_continue` job pends forever as
`DependencyNeverSatisfied` — deferred rules silently never run and the stuck job
lingers in the queue.

**Fix direction**: add the flag to the template (and consider `afterany` + in-job
replan, since remake itself knows what is up to date).

### 10. Dry-run rewrites job specs and submit.sh — CONFIRMED
`slurm_executor.py:173,179,202` vs skip at 206-208

`dry_run=True` skips only the final `submit()`; specs, sbatch scripts and submit.sh
are all rewritten. Consequences: (a) `remake task-info` pairs **old** sidecar jobids
with an `array_index` computed from the **new** spec (`last_submission`,
lines 113-117) — wrong `%a.out`/element attribution; (b) a later `remake resubmit`
executes the dry-run-generated submit.sh as if it were the last real plan.

**Fix direction**: write to a staging path in dry-run mode, or generate to strings
and only persist when submitting.

### 11. Remakefile path interpolated unquoted into generated scripts — CONFIRMED
`slurm_executor.py:48,61,72`; source `loader/__init__.py:56`

`rmk.remakefile` is the user-typed path verbatim, formatted with no quoting into the
bash templates. A project path containing a space (home dirs, group workspaces)
word-splits on the compute node: remake receives `my` as the remakefile — every job
fails at runtime after queueing. Loud rather than silent, hence ranked low, but the
allocation is wasted and the error surfaces far from the cause. (Other interpolations
are rule-name-derived `.remake/` relative paths and are safe.)

**Fix direction**: `shlex.quote()` every interpolated path in all three templates and
in `_submit_lines`.

### 12. Stale sidecar + recycled jobid falsely marks rule queued — PLAUSIBLE
`slurm_executor.py:327`

Sidecars are never aged out; `_queued_jobids` is a bare membership test of recorded
ids against all of the user's active jobs. A recycled jobid (default MaxJobId ~67M
wraparound, or admin `FirstJobId` reset after maintenance) colliding with an
unrelated active job silently skips the rule and wires downstream
`afterok:<unrelated job>` (amplified by `--kill-on-invalid-dep=yes`). Real but rare —
needs a long-lived project dir straddling a jobid reset.

**Fix direction**: stamp the sidecar with submit time + cluster name and ignore it
when implausibly old; per-submission spec files (see theme note) also moot this.

## Cleanup findings (verified)

### C1. Dual sidecar encodings, duplicated parsing, and an already-bitten consumer — CONFIRMED
`slurm_executor.py:269` vs `281` (writers), `109-112` vs `323-327` (readers)

The sidecar encodes "last submission's jobids" two ways (`slurm_array_job_id` scalar
vs `slurm_job_ids` list); the normalize-to-list dance is copy-pasted in
`last_submission` and `_queued_jobids`, and
`tests/benchmarks/bench_slurm_failure.py:199` reads only the array key — silently
getting `None` whenever stage2 is submitted individually (e.g. `--n` below the
array threshold of 10). Always write `{"slurm_job_ids": [...]}` and add one shared
reader.

### C2. Array/individual dual mode is largely a remnant — CONFIRMED
`slurm_executor.py:40-65`, `184-187` vs `266/274`, `262-282`

The two templates differ only in the `--array` header, `-o/-e` placement, and
`$SLURM_ARRAY_TASK_ID` vs `$1`; the `JOB_<rule>` shell-var naming is derived
independently in `run_tasks` and `_submit_lines`; the dual sidecar encoding (C1)
exists only because of the split. SLURM accepts `--array=0-0`. The design doc's
original rationale (per-element fan-in deps, `remake3_design.md:790-794`) is not what
the code implements — eligibility is purely `count >= threshold`. Submitting every
rule as an array deletes the second mode and half the state space (keep
`array_threshold` as an escape hatch for clusters with restrictive MaxArraySize).
This also fixes finding 2's sidecar window structurally.

### C3. Every array element parses the whole spec file — CONFIRMED
`remake_cmd.py:420-422`, `json.dumps(..., indent=1)` at `slurm_executor.py:222`

Each of N elements reads and JSON-parses the entire `<rule>.json` to pick
`specs[index]`: O(N²) aggregate bytes worst case (a 20k-task rule → multi-MB file ×
20k reads over NFS at array start; NFS client caching softens the typical case).
`indent=1` inflates the file for zero benefit. Cheaper: per-index spec files, or
JSONL + byte-offset index; at minimum compact separators.

### C4. submit.sh execution logic duplicated with a hardcoded path — CONFIRMED
`slurm_executor.py:300-307` vs `remake_cmd.py:432-445`

`SlurmExecutor.submit()` and `remake_resubmit` duplicate the run-capture-raise block,
and remake_cmd hardcodes `.remake/submit.sh` separately from `self.submit_path`.
Extract one `run_submit_script(path)` in slurm_executor (imported by remake_cmd like
`last_submission`/`squeue_snapshot` already are). Fixing finding 6 will rework this
anyway.

### C5. Sbatch-config merging spelled out three times — CONFIRMED
`slurm_executor.py:146-147`, `225-227`, `287-288`

The set of remake-only pseudo-keys that must not become `#SBATCH` lines
(`array_threshold`, `array_throttle`) lives implicitly in scattered `pop()` calls
across `__init__`, `_write_sbatch` and `_write_continuation`. A new pseudo-key missed
in one site leaks into `_sbatch_opts` and produces an invalid `#SBATCH` directive.
One `_effective_sbatch_config(rule=None)` helper should own the merge and the
pseudo-key list.

## Noted but not verified (lower priority)

- `_dependency` re-materialises and deep-compares full kwargs lists per (rule, dep)
  edge (`slurm_executor.py:255`) — O(n·kwargs) per edge at 20k-task scale; a per-rule
  signature on `_SubmittedRule` would do.
- No tasks-per-element chunking: each element pays full interpreter + import +
  remakefile-load cost (~1-3 s, NFS-resident) — dominates for fine-grained tasks.
- Sidecar JSON generated via hand-escaped `echo` in Python f-strings (two escape
  layers, `slurm_executor.py:269,280-281`) — one wrong backslash yields malformed
  JSON that disables already-queued detection; C1/C2's rework should replace it.
- The `.remake/jobs` path scheme is spelled out independently in `last_submission`,
  the executor, and `remake_cmd.run_array_task` — wants module-level path helpers.
- `Remake.task_info` (core) reaches into the SLURM executor module for
  `last_submission` — core should consume an interface, not an executor's file
  format.
