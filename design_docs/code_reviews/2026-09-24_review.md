## Summary

No finding corrupts data outright, but four themes stand out:

1. **Change detection leaks in both directions** — the core promise.
   Spurious mass reruns (decorator edits, `set`s in `uses`, a Python 3.13
   upgrade) and silent misses (shifted/windowed inputs across a shared
   matrix, scope-analysis blind spots, lossy `repr` of callables/arrays,
   shrinking fan-ins).
2. **The parallel executors diverge from singleproc.** multiproc/dask never
   record `run_seq` (bug 01 is back under `-E multiproc`); `SystemExit`,
   worker crashes and Ctrl-C are handled far worse than ordinary exceptions.
3. **DB lifecycle robustness** — a zero-byte DB bricks the pipeline;
   migrations are non-atomic and race.
4. **Error surface** — many user errors escape as tracebacks with exit 1
   (colliding with "tasks failed"), queries silently match nothing, and some
   failures leave no traceback anywhere.

Suggested order of work is at the end.

## Bugs — high severity

### H1. multiproc/dask record `run_seq = NULL` → durable rerun propagation (bug 01) silently disabled — VERIFIED
`executors/multiproc_executor.py:50`, `executors/dask_executor.py:41`
(`SidecarWriter()` without `run_seq`; only SLURM passes it,
`remake_cmd.py:474`) → stored NULL (`sqlite3_backend.py:571`) → planner skips
the backstop when `rec.run_seq is None` (`planner.py:455`).

**Scenario**: bug 01's scenario 2 under `-E multiproc` or `-E dask`: edit
upstream A, `run -Q "rule=='A'"`, then plain `run` → B never reruns and
keeps the stale result. Verified: every `run_seq` NULL after a multiproc run;
after the A edit + filtered run, `run -n` says `0 task(s) would run` and
`b/1.txt` is still `1v1`. NULLs also blind `set-state` cascading.

**Fix**: pass `rmk.metadata.current_run_seq()` from the parent through
`initargs`/`_run_spec` into `SidecarWriter(run_seq=...)`; add multiproc and
dask variants of `test_partial_target_rerun_propagates_to_downstream`.
Patch-lane eligible (corrects what was wrongly recorded).

### H2. Editing the `@rule(...)` decorator reruns every task of the rule — VERIFIED
`core/scope.py:161-170` (`inspect.getsource` includes decorators),
`core/rule.py:48`, `util/code_compare.py:21-38` (compares `decorator_list`).

Run code is meant to be the function body (docs: "remake hashes each rule's
function body", `rules-and-tasks.md:176`) but covers the whole decorated
statement, so literal `matrix=`, `config=`, `depends_on=`, `name=` edits
count as code changes.

**Scenario**: bump `config={'slurm': {'mem': ...}}` after an OOM (the
`ex8_zarr_slurm.py` idiom) → every successful task reruns, plus everything
downstream. Adding a year to an inline `matrix={'year': [...]}` reruns the
old years too (but not when the list is a module constant — inconsistent).
Verified: `why` → `run code changed` with the `@rule(... mem ...)` line as
the diff.

**Fix**: strip `decorator_list` in `CodeComparer` on both the stored and
current side (no migration needed); keep raw source for the `why` diff.
Removes a spurious trigger, so patch-safe.

### H3. A shared matrix is assumed to mean element-wise dependency → under-rerun — VERIFIED
`planner.py:55-58` (`_same_matrix`), `:405-406`, `:70` (durable backstop),
`:113` (cascade), `:139` (`upstream_failed`).

Any downstream with `matrix=upstream.matrix` is assumed to read only the
same-kwargs upstream task. Wrong for shifted inputs
(`inputs=lambda year: {'prev': f'a/{year-1}.txt'}`) and for per-element
tasks that read many upstream elements. Contradicts the design's "over-
rerunning is possible … never under-rerunning" (`design.md:495-497`).
Failure-skip is also mis-scoped the same way.

**Scenario** (verified): `b[year]` reads `a[year-1]`; after forcing
`a[2001]`, `why` says `b[2001]` will run and `b[2002]` — the actual consumer
— is up to date.

Note the SLURM executor already solved the *scheduling* half of this (July
review finding 7): `_elementwise()` (`slurm_executor.py:319`) decides
`aftercorr` vs `afterok` from resolved paths, not matrix equality. So a
stencil pipeline on SLURM is *scheduled* correctly but *rerun* incorrectly —
two sources of truth for one question.

**Fix**: derive task-to-task dependencies from resolved paths — see
[Appendix A](#appendix-a-fix-design-for-h3). Lane: 0.9.0 (core planner
change with a cost to manage), though compatibility.md would permit it as a
patch — reruns it causes are of outputs wrongly recorded as fresh. The
failure-skip part alone is 0.8.x-safe.

### H4. A `set` in `uses=` (or set-ordered dict in an io spec) reruns on every invocation — VERIFIED
`scope.py` `uses_parts` (`repr(value)`), `io_hash` (`repr` → `ast.dump`),
exact string compare at `planner.py:392-396`, `:243`.

String hash randomisation makes `repr({'tas', 'pr', ...})` differ per
process. **Scenario**: `VARS = {'tas', 'pr', 'ua', 'va', 'rlut'}` with
`uses={'VARS': VARS}` — verified three consecutive `run -n` after a
successful run each say `1 task(s) would run`. Same for a fan-in
`inputs={v: f'out/{v}.txt' for v in VARS}`. Sets of variable/model names are
a very common config idiom. Related false positive: reordering dict keys in
`uses` reruns (dict order is not semantic under `==`).

**Fix**: canonical value rendering (sort set/frozenset elements; sort dict
keys) for `uses` and io specs; or at least warn on sets.

### H5. Upgrading Python ≤3.12 → 3.13+ reruns (nearly) every task — VERIFIED (mechanism)
`scope.py` `_normalised_src` / `_normalised_source` store `ast.dump()`
strings for io specs and callable `uses`, compared by exact string.

Python 3.13's `ast.dump` omits empty fields by default (`show_empty=False`).
Verified: `ast.dump(ast.parse("{'o': 'x'}"))` ends `..., type_ignores=[])`
on 3.12 and `...]))])` on 3.13. Nearly every rule has an io spec →
`inputs/outputs spec changed` everywhere. `requires-python >=3.10`, and the
JASMIN/lapsedpacifist envs will cross this line. (Run code is unaffected — it
is stored raw and re-parsed.)

**Fix**: store raw source/repr and compare with the version-independent
`_compare_ast` as run code does, or a custom canonical dumper; normalise both
sides so existing DBs don't mass-rerun.

### H6. `sys.exit()` / `KeyboardInterrupt` inside a task aborts the run silently; `sys.exit(0)` exits 0 — VERIFIED
`core/remake.py:781` catches only `Exception`; so do the executors
(`singleproc:30`, `multiproc:64`, `dask:50`); multiproc re-raises the
worker's `BaseException` via `future.result()` (`multiproc:126`).

**Scenario**: a task calls a CLI `main()` (argparse/click) that calls
`sys.exit(0)`. Verified: run stops after task 2 of 4, **exit 0**, no error,
no failure recorded, `info` shows 3 pending. `sys.exit(3)` → silent rc 3.
Under dask it kills the worker (see H7).

**Fix**: in `run_task` catch `SystemExit` (arguably all `BaseException`
except `KeyboardInterrupt`), record as failed, re-raise wrapped as a
`RemakeError` subclass so executors treat it as an ordinary failure.

### H7. A worker crash (OOM kill, segfault, `os._exit`) aborts the run; dask re-executes completed tasks — CONFIRMED
- **multiproc** (`multiproc_executor.py:126`): `BrokenProcessPool` escapes
  `run_tasks` → traceback, the crashed task is not recorded (stays pending,
  so the next run crashes again), in-flight tasks aborted, end-of-rule
  `ingest_sidecars` skipped.
- **dask** (`dask_executor.py:121-124`): the nanny restarts the worker; the
  `futures` dict pins completed results on the dead worker, so the scheduler
  **recomputes already-completed tasks** (observed: a task's print appears
  twice), then retries the crasher 4× and `KilledWorker` escapes.

OOM-kill is a realistic outcome for the target workloads.

**Fix**: multiproc — catch `BrokenProcessPool` per future, record in-flight
tasks failed ("worker died"), rebuild the pool and continue. dask — release
futures once read, `retries=0` / `allowed-failures=0`, catch `KilledWorker`
per future and record a failure.

### H8. Duplicate rule names are accepted; tasks share keys and ping-pong forever — VERIFIED
`core/remake.py:85-96` (`add_rules` dedups by identity only), `dag.py:17`
(`rules_by_name` keeps the last), `task.py:42-43` (key = sha1 of
`name:kwargs`), `remake.py:221` (`task_from_spec` returns the first).

**Scenario**: two modules via `rules_from_modules` each defining `process`,
or a clashing `name=`. Verified: plan lists every key twice; both rules
overwrite each other's `run_code_id` so each run reports `run code changed`;
multiproc/SLURM (`task_from_spec`) execute the first rule for both. Notebook
variant: re-executing a cell with `@rule` + `rules_from_current_module()`
appends a second `Rule(a)` and `run()` executes 4 tasks for a 2-task rule.

**Fix**: raise `RemakeError` on a name clash with a *different* rule in
`add_rules`/`finalize`; for notebook re-execution, replace same-named rules
(with a warning).

## Bugs — medium severity

### M1. Scope analysis passes real undeclared globals, even under `strict_scope=True` — CONFIRMED
`scope.py` `undeclared_names`, `_is_environment`. Three gaps:
(a) **instances of stdlib classes** are treated as environment because
`value.__module__` resolves via the class — `DATA_DIR = Path(...)`,
`re.compile(...)`, `Decimal`, `Counter`; (b) names are skipped because they
**shadow a stdlib module/builtin name** regardless of value — `site = 'CHIL'`,
`time`, `code`, `token`, `input`, `id`; (c) **attribute access on
project-local modules** (`import params; params.FACTOR`) is invisible.
**Scenario**: `Remake(strict_scope=True)`, rule uses `OUTDIR / site`; change
both → no error, no warning, 0 reruns. **Fix**: only modules/classes/
functions can be environment, never instances; name-based skip only when the
bound value *is* that module/builtin; modules count as environment only if
`__file__` is in stdlib/site-packages, else warn.

### M2. Helpers/constants defined *below* a rule are never scope-checked — CONFIRMED
`check_scope` runs at decoration, when later names aren't in `__globals__`
(ignored as "left to fail naturally"); `remake.py:92` only re-checks when the
Remake-level `strict_scope` is set. Rule-level `@rule(strict_scope=True)` is
therefore *weaker* than Remake-level. "Rules first, helpers at the bottom" is
a common layout. **Fix**: (re-)run `check_scope` for every rule at
registration.

### M3. Sourceless callables in `uses` collapse to a type label — CONFIRMED
`scope.py` `function_source` fallback `'<unsourced:{type}>'`; `callable()`
wins over `repr` in `uses_parts`. Undetected: `partial(scale, factor=2→3)`,
a callable instance `Scaler(2→3)` (even with a custom `__repr__`),
`np.float32→np.float64`, `np.log→np.log10`, `math.sqrt→math.exp`. User docs
say functions in `uses` are compared by source. **Fix**: partial → source of
`func` + repr of args; other non-function callables → `repr`; always include
`__module__.__qualname__`.

### M4. numpy/pandas `repr` is lossy → real `uses` changes missed — CONFIRMED
Arrays >1000 elements are summarised with `...` (`W[1000] = 5` → 0
reruns); floats print at 8 significant digits; DataFrames are truncated.
**Fix**: special-case ndarray (dtype+shape+`tobytes()` hash) and pandas
(`hash_pandas_object`); bring forward the user hash hook the design doc
mentions; document.

### M5. A zero-byte or partially created DB bricks the pipeline permanently — VERIFIED
`sqlite3_backend.py:143-153`: `create_db` is decided by `Path.exists()`, but
`sqlite3.connect` creates the file before `executescript(SQL_SCHEMA)`.
**Scenario**: first run dies during schema creation — disk/quota full (JASMIN
`$HOME` has filled before) or Ctrl-C → 0-byte file → every later command:
`sqlite3.OperationalError: no such table: task` until the user deletes
`.remake/remake.db` by hand. Verified with `touch .remake/remake.db`.
**Fix**: decide creation by checking `sqlite_master` for the `task` table;
run the schema inside `BEGIN EXCLUSIVE … COMMIT`.

### M6. Migrations are non-atomic, non-idempotent and race — CONFIRMED
`sqlite3_backend.py:184-266`: `_add_missing_columns` runs before
`isolation_level` is set, so each `ALTER TABLE` autocommits.
(a) Concurrent first opens after an upgrade (continuation jobs; `info` while
`run` starts) all `ALTER ADD wall_s` → `duplicate column name` crashes in
the losers (140/160 openers in a stress repro; DB fine afterwards). Fresh-DB
concurrent open → `table code already exists`.
(b) An interrupted 0.8.0a0 inline-hash migration is never resumed: columns
exist, so it's skipped forever → `uses_code_id` NULL, every task of any rule
with `uses=` reruns, `uses_hash` (272 MB in the field) never reclaimed.
(c) `CREATE TABLE meta` commits before its `INSERT` (PLAUSIBLE, µs window) →
`_allocate_run_seq` `TypeError` forever.
**Fix**: one `BEGIN EXCLUSIVE` transaction for all migrations, re-reading
`table_info` inside the lock; tolerate "duplicate column"; drive backfills off
data state (`uses_hash IS NOT NULL AND uses_code_id IS NULL`); adopt
`PRAGMA user_version`.

### M7. `-Q` and upstream state: filtered runs disagree with `why` and don't guard upstream — CONFIRMED
Two related problems:
- **Backstop blinded by the filter** (`planner.py:361`, `:467-471`):
  `task_run_seq[dep]` holds only predicate-matching upstream tasks, while
  `explain_tasks` plans unfiltered. After `run -Q "rule=='a'"`, the
  debugging-guide idiom `run -Q "rule=='b'"` says "Nothing to do" while
  `why -Q "rule=='b'"` says "will run: yes" and unfiltered `info` shows b
  stale. (Bug 01 covered only the unfiltered follow-up.)
- **Selected downstream runs without its upstream**: fresh `ex1`, `run -Q
  "rule=='summarise'"` runs `summarise` alone → FileNotFoundError, recorded
  failed; with a stale-but-present upstream output it silently builds from
  stale input.
**Fix**: build `task_run_seq` from the unfiltered upstream (or a DB lookup) —
the query limits what runs, not which state is consulted; skip (with a
message) selected tasks whose upstream would rerun or never succeeded, and
offer an upstream-closure option (feature F1).

### M8. Fan-in doesn't rerun when its upstream matrix shrinks / a callable io spec reads a global — CONFIRMED
`scope.py:204-217` (`io_hash` = callable source only), `planner.py:399-409`.
Remove 2002 from `YEARS` → `agg` (inputs built in a callable over `YEARS`)
still reports 3 years; `run` "Nothing to do", `why` "up to date". (A
dict-literal fan-in is caught because `repr` sees the values.) **Fix**: store
a digest of each task's *resolved* input/output path list and compare it
(new trigger → 0.9.0); meanwhile document `uses={'YEARS': YEARS}` on fan-ins.

### M9. `run` exits 0 when rules stay blocked (deferred matrix never resolves) — VERIFIED
`remake.py:729-733`, `:748` (returns `nfailed`). A `@deferrable` matrix
waiting on a mistyped path or a permanently failing upstream → only a
WARNING "Blocked rules (matrix not ready): b", exit 0 (verified); CI treats
it as success. `Defer.paths` is never read anywhere, so the user isn't told
what's missing; the same message is shown when the real cause is an upstream
failure. **Fix**: non-zero (distinct) exit when blocked rules remain; carry
`e.paths` into the message; distinguish "upstream failed".

### M10. Ctrl-C doesn't stop a multiproc run; SIGTERM leaves orphan workers — CONFIRMED
`multiproc_executor.py:97-131`: leaving the `with ProcessPoolExecutor` block
calls `shutdown(wait=True)` without `cancel_futures`. Terminal Ctrl-C kills
in-flight tasks, then **queued tasks run to completion** (for a 1000-task
rule, Ctrl-C ≈ "finish the rule"). SIGTERM to the parent: workers survive,
start new tasks after the parent dies and write sidecars — a new `remake run`
then races them on the same outputs (no run lock, M15). **Fix**: on
`BaseException`, `shutdown(wait=False, cancel_futures=True)` and terminate
workers; SIGTERM handler raising `KeyboardInterrupt`; clean "interrupted: N
done / M remaining" message instead of a traceback.

### M11. Failures before the rule function runs are not recorded or reported — VERIFIED
`core/remake.py:763-771`: output-dir `mkdir`, `exec_function(...)` and
`task.inputs` (callable io resolution) sit outside the `try`. **Scenario**
(verified): output `blocker/x.txt` where `blocker` is a file → "1/1 tasks
failed", **no traceback anywhere**, and `info` shows the task *pending*, not
failed; `info -F` empty. **Fix**: move them inside the `try` (keep resource
capture around `fn` only).

### M12. Failure tracebacks never reach per-task logs; multiproc/dask events never reach `remake.jsonl` — CONFIRMED
- `core/remake.py:787-790` logs `failed: … after Ns` with `.error()` but no
  `opt(exception=True)`, so `task-log` for any failed task (run-task,
  run-array-task — i.e. every SLURM failure — and multiproc) shows one line;
  the traceback lives only in the DB/`.err`. The `multiproc_executor.py:65`
  comment ("recorded (sidecar + log)") is wrong.
- Singleproc writes no per-task log at all, yet `info -F`, `task-info` and
  `debugging.md` point users at one; a stale log from an earlier multiproc
  attempt then sits next to `status: success`.
- Workers `logger.remove()` and add only a text sink (`multiproc:48,60`,
  `dask:46`), so `task_complete`/`task_failed` JSONL events (incl. the new
  resource fields) are singleproc-only.
**Fix**: `logger.opt(exception=True).error(...)`; per-task sink (or truncate
stale logs) in singleproc; emit task events from the parent as futures
resolve.

### M13. The Python API is not anchored to the remakefile's directory — VERIFIED
`loader/__init__.py:41-60` vs the CLI's chdir (`remake_cmd.py:955-971`).
`load_remake('/abs/pipe.py').status_summary()` from another cwd reports
everything pending and **creates a fresh `.remake/` in the caller's cwd**
(verified); `rmk.run()` would rebuild everything relative to the notebook's
cwd. Undercuts the roadmap's "remake-as-a-library" headline. **Fix**: record
the remakefile dir in `load_remake` and resolve the DB and relative paths
against it (or a documented `chdir=True` context); at minimum warn when cwd
differs.

### M14. Queries silently match nothing on builtins or typos; bad queries give raw tracebacks — VERIFIED (partly KNOWN)
`planner.py:36-43`: `__builtins__` stripped and every `NameError` treated as
"no match". Verified: `-Q "n in range(1,3)"` and `-Q "nn == 1"` both →
0 tasks, no error; `run -Q` then prints "Nothing to do", exit 0 — a typo is
indistinguishable from "done", and `set-state -Q` silently no-ops.
`-Q "n =="` → raw `SyntaxError` traceback (KNOWN: todos "eval-based query
filter"). **Fix** (independent of the planned AST parser): check the
query's `co_names` against rule kwargs + `rule`; allow-list safe builtins
(`range`, `len`, `min`, `max`, `abs`, `int`, `str`, `set`); warn on 0 matches;
wrap compile/eval errors in `RemakeError`.

### M15. No local run lock: concurrent `remake run`s double-execute every task — CONFIRMED
Two `remake run` in one dir 0.3 s apart both report `ran 5 task(s)` and
write the same outputs concurrently. SLURM has the squeue guard; local
executors have nothing. **Fix**: a lock/PID file in `.remake/` with a clear
message and `--unlock` for stale locks.

### M16. Under `check_outputs='fallback'/'always'`, partial outputs of an interrupted first run are adopted — CONFIRMED
`planner.py:420-422`: a record-less task with existing outputs is treated as
done; no "started" marker, outputs written in place. SIGINT mid-write, rerun
→ the half-written file is adopted and consumed downstream. Safe under the
default `never`. **Fix**: record a "started" state (DB or sidecar) that
fallback won't adopt, or document and recommend atomic writes.

### M17. Sidecar ingest overwrites newer DB records; `run_seq` can go backwards — CONFIRMED
`sqlite3_backend.py:539-555` (`ON CONFLICT DO UPDATE` unguarded); `run-task`
writes directly without ingesting first. An old FAILED sidecar (un-ingested
SLURM element, or a multiproc parent that died) + a manual `run-task` SUCCESS
→ the next `info` ingests the sidecar and reverts the row to failed with the
older timestamp and run_seq. The reverse (old SUCCESS masking newer FAILED)
is also possible. **Fix**: upsert guard on `last_run_timestamp`/`run_seq`;
ingest before `run-task` writes.

### M18. Resource capture under-reports child-process peak memory — CONFIRMED
`util/resources.py:243-254`. `RUSAGE_CHILDREN.ru_maxrss` is the largest
child *ever reaped by this process*, counted only if it grew: in pooled
workers (and singleproc) a later task spawning a smaller child reports only
the Python floor (task1 617 MiB, task2 50 MiB); concurrent children are not
summed (3×300 MiB → 317 MiB); parent and child combine as `max`, not sum.
The figure exists to size memory requests, so under-reporting causes OOMs.
**Fix** (short): mark `rss_method` as unmeasured/`sample-self` when children
were reaped but the high-water mark didn't grow; document max-vs-sum. (Real
fix: process-tree sampling or cgroup `memory.peak`, already deferred.)

### M19. Task keys unstable for numpy scalars / enums — CONFIRMED
`dag.py:99-113` (`isinstance` scalar check accepts subclasses), `task.py:42`
(`repr` in the key). `np.float64(0.5)` and `StrEnum`/`IntEnum` pass, but the
key changes across the SLURM JSON round-trip (float/str come back) and across
numpy 1→2 (`0.5` → `np.float64(0.5)`) — orphaning every record, i.e. a mass
rerun. **Fix**: exact-type check (`type(v) in _SCALAR_TYPES`) or canonicalise
(`float(v)`, `str(v)`) at expansion.

### M20. Quadratic diagnostics: `why`, `info --reasons`, `lint` — CONFIRMED
`planner.py:265-266` scans all of `runnable` per task per dep; `:288-298`
re-expands the dep and rebuilds its run_seq map per explained task —
`why -Q b` 0.34/1.28/4.6 s at N=500/1000/2000 (≈2 min at 1e4). `lint`
near-miss search (`remake.py:564`, `difflib.get_close_matches` over all
upstream outputs per unmatched input) 0.43/0.97/3.44 s at 500/1000/2000.
Both miss the 1e4×1e2 scale target (bug 04 fixed the record re-query, not
this). **Fix**: compute per-dep maps once and index `runnable` by
`(rule, kwargs)`; cap near-misses per (rule, dep) or compare templates.

## Bugs — low severity

Planner / DAG / rules
- **L1. Matrix validation gaps** (`dag.py:61-81,118-122`, `rule.py:86-87`)
  — `matrix={'site': 'oxford'}` iterates characters (duplicate `o` executed
  twice); duplicate rows run twice (racing writers under multiproc);
  `{'year': 2000}` → bare `TypeError`; callable matrix returning a dict →
  `KeyError: 0`, generator → not subscriptable; heterogeneous `list[dict]`
  passes (only row 0 checked) and fails per task; a generator axis gives 3
  tasks then 0 after a replan; `{'x': 1}` vs `{'x': True}` conflated in
  element-wise propagation. Fix: reject str/non-iterables, materialise axes,
  validate every row and uniqueness.
- **L2. List-valued entries in dict `inputs`/`outputs` are stringified**
  (`task.py:24-29`): `{'files': ['a/{i}', 'b/{i}']}` → one str
  `"['a/1', 'b/1']"`; `lint`/`check_outputs` see a bogus path. Raise
  `SignatureError` or format each element. (Related: KNOWN bug 02 —

## Rough edges — API and CLI

**Flag consistency**
- Global flags (`-D`, `--colour`, …) only work *before* the subcommand;
  `remake info f.py -D` is "unrecognized arguments". Use argparse `parents=`.
- `--json` is missing on `why`, `run -n`, `set-state` (the ones agents/skills
  most need); `run-task` takes only a key (no `-Q`); `ls-tasks --check` vs
  `--check-outputs` elsewhere, and `--check` without `-i/-o` is silently
  ignored; `why`/`info` don't accept `--check-outputs`, so can't explain what
  `run --check-outputs` will do.
- `-j N` without `-E multiproc` is silently ignored (runs singleproc). Warn,
  or imply multiproc.
- `set-state` validation messages use API names ("success / pending",
  "check_outputs") rather than `--success/--pending`; use a required
  mutually-exclusive group.
- Bare `remake` prints help and exits 1 (argparse's own error path exits 2).

**Help and docs drift**
- `-E` help and the running.md executor table omit `dask`; `-j` help says
  "multiproc" only; `run` help "Run all pending tasks" (but it also runs
  stale/failed — "pending" means never-run in `info`); module docstring
  "Minimal surface: run, run-task, info, version".
- cli.md: "every command takes a remakefile path" (`version` doesn't); omits
  `--json` for five commands; `lint` exit codes undocumented; running.md exit
  codes say only "non-zero = task failed"; discussion.md references a
  nonexistent `run -I`.
- `rule()`'s docstring says "See design.md" (not on the docs site);
  `Remake` has no class docstring; no user-guide page for API/notebook use.

**Output at scale (1e4 tasks)**
- Bare `why` prints a 3–4-line block per runnable task (60–80k lines, 9 s
  for 2e4 never-run tasks); `run` logs one INFO line per task and the only
  quieter level (`-W`) drops the summary too — a per-rule progress level is
  missing; `rule-info` prints full matrix value lists; `run -n` has no
  per-rule counts or reasons.
- `info`/`run -n` show ex10's `summarise_events` as deferred while
  `ls-tasks`/`rule-dag -N` list it as one task.
- JSON shapes: `lint` `example` is a str or a dict depending on the kind;
  `info --json` deferred rows lack count keys; `rule-dag --json` adds `rules`
  only with `-N/-M`; no schema/version field; `ls-tasks --json` builds the
  whole list in memory.

**Python API**
- remake emits DEBUG logs to stderr in library use (loguru default sink):
  `logger.disable('remake')` at import, enable in the CLI.
- `rmk.why()` returns a bare generator; `rmk.run(executor=...)` needs an
  instance built with `rmk` (no `executor='multiproc', nproc=` form;
  `MultiprocExecutor(rmk)` fails unless `rmk.remakefile` is set); `run()` has
  no `dry_run`/`check_outputs` params (the CLI mutates `rmk.check_outputs`).
- Method names don't mirror the CLI (`status_summary`↔`info`,
  `explain_tasks`↔`why`, `rule_from_name`/`task_from_key`/`select_task`);
  `task_info(task)` takes a Task, the CLI a key.
- `@rule` without parentheses → `TypeError: rule() takes 0 positional
  arguments`; detect and explain.
- A callable `inputs`/`outputs` taking `**kw` receives no kwargs
  (`task.py:21-22`) → paths like `a/None.txt`; `check_io_spec` accepts it.
- `matrix=[]` on a rule with parameters is a `SignatureError` at decoration
  (a temporarily empty filtered list can't be declared).
- No `Remake.close()`/context manager; shutdown relies on `__del__` (related
  to the KNOWN py3.14 ResourceWarning).
- `Executor.run_tasks` returning `None` counts as 0 failures (easy to get
  wrong in a custom executor); `handles_deferred=True` executors must accept
  an undeclared `(tasks, deferred)` signature.
- `build_rule_dag` mutates `rule.depends_on` in place (strings → Rules) on
  free-standing, importable Rule objects.

**Runtime behaviour**
- multiproc/dask put a barrier between rules even when independent; a new
  pool / LocalCluster per wave (every worker reloads the remakefile per wave).
- Task stdout/stderr under multiproc/dask goes to the parent terminal,
  interleaved, never into the per-task log; per-task log level fixed at
  DEBUG (`-T` doesn't reach workers).
- Failure-skip for non-shared matrices is conservative (one failed
  `process[oxford,2010]` skips `aggregate` for all sites) with nothing in the
  log saying why.
- `why` labels decorator edits "run code changed" with no hint that the body
  is unchanged (moot if H2 is fixed); `from numpy import mean` warns but
  `np.mean` doesn't.
- After `set-state --success`, `task-info` pairs the set-state timestamp with
  an older execution's resources; set-state overwrites `exception` with `''`
  (the failure's traceback is lost); full tracebacks stored uncapped;
  sidecars not `fsync`ed before rename (a node crash on NFS/Lustre can leave a
  zero-length sidecar).
- Empty pipeline or a forgotten `rules_from_current_module()` gives no
  warning ("Nothing to do", exit 0).

## Appendix A: fix design for H3

**Principle**: which upstream tasks a downstream task depends on is a
property of its resolved *inputs*, not its matrix. Equal matrices say the
two rules have the same task set; they say nothing about which upstream
output each task reads. Replace `_same_matrix` with a per-edge task-to-task
map derived from paths — generalising SLURM's `_elementwise()` from a yes/no
answer to a full map, and sharing one implementation between planner and
executor.

### 1. Per-edge dependency map

```python
# core/deps.py (new; used by the planner and the SLURM executor)
ALL = object()   # can't tell precisely: depends on every upstream task

def edge_map(dep_tasks, tasks):
    producer, shared = {}, set()
    for t in dep_tasks:
        tid = frozenset(t.kwargs.items())
        for tok in t.outputs.values():
            p = _norm(tok)            # token identity, os.path.normpath'd
            if p in producer:
                shared.add(p)         # e.g. one zarr store region-written by all
            producer[p] = tid
    m = {}
    for t in tasks:
        paths = {_norm(p) for p in t.inputs.values()}
        hits = paths & producer.keys()
        if not hits or hits & shared:
            m[frozenset(t.kwargs.items())] = ALL   # ordering-only dep / shared output
        else:
            m[frozenset(t.kwargs.items())] = {producer[p] for p in hits}
    return m
```

Shifted inputs give `b[2002] → {a[2001]}`; a climatology-style reader maps
to every upstream year; the `inputs=a.outputs` idiom gives `b[y] → {a[y]}`
(today's behaviour). Anything uncertain degrades to `ALL` (conservative).

### 2. Consumers — the four `_same_matrix` call sites

| Site | Today | With the map |
|---|---|---|
| Same-pass propagation (`planner.py:399-409, 453`) | same-kwargs upstream only | rerun if `m[t] is ALL and dep reruns`, or `m[t] & rerun_kwargs[dep]` |
| Durable backstop (`_max_upstream_run_seq`) | same-kwargs run_seq | max run_seq over `m[t]` |
| Failure-skip (`upstream_failed`) | same-kwargs failure | `m[t] & failures[dep]` |
| set-state cascade (`cascade_settled`) | `[task_kwargs]` | `m[t]` |

SLURM's `_elementwise(a, b)` becomes "`m[b_i] == {a_i}` for every i" over
the same map.

**Side benefits**: fan-ins across *differing* matrices become precise too
(`aggregate[site]` reading `process[site, *]` reruns/skips per site instead
of all sites — the conservative failure-skip rough edge); `why` can name the
actual upstream ("upstream a[year=2001] reruns").

### 3. Cost control

Resolving every input and output path per plan costs ~2 s / 0.6 GB per 1e6
paths (`bench_field_scale` baseline) — too much to pay unconditionally.

- **Template fast path**: if `rule.inputs is dep.outputs` (or each input
  template is literally an upstream output template) and the matrices match,
  the edge is element-wise by construction — no resolution. Most pipelines
  take this path.
- **Lazy construction**: build an edge's map only when needed — the upstream
  has a partial (non-`'all'`) rerun set or failures; for the backstop, only
  when the upstream's max run_seq exceeds some downstream task's run_seq
  (cheap pre-check).
- **Cache per edge** keyed on both rules' io hashes + a matrix fingerprint,
  if benchmarks show it's needed.

### 4. Tests

Shifted (`year-1`), stencil (t−1, t, t+1), climatology (reads all),
identity idiom (fast path), shared zarr output (`ALL`), ordering-only
`depends_on` (`ALL`) — each through propagation, the cross-invocation
backstop, failure-skip and the cascade; a precise fan-in; SLURM
`aftercorr`/`afterok` choices unchanged; planning time on
`bench_field_scale`.

### 5. Limit and contract

The map is only as good as the declared inputs: a task that reads
undeclared upstream files (e.g. globbing `a/*.txt`) is invisible. SLURM's
`aftercorr` already relies on this contract; the empty-hits → `ALL` rule
covers pure ordering-only dependencies. Document it in
`docs/guide/rules-and-tasks.md`.

### 6. Lane

compatibility.md's patch rule forbids reruns "whose cause is the upgrade
itself" but allows rerunning "what was wrongly recorded as fresh" — which is
what this fixes. It could therefore be a patch; it is placed in **0.9.0**
because it changes planner core and carries a performance cost to manage.
The failure-skip consumer alone is small and 0.8.x-safe.
